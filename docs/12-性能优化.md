# 12 · 性能优化

> 定位：哪里会慢、怎么测、怎么优化、优化的边界在哪
> 状态：v1.0
> 原则：**先测量，后优化。提升 < 20% 就回滚**

---

## 0. 优化原则

| 原则 | 说明 |
|:---|:---|
| 先测量 | 没有 profiling 数据的优化都是瞎猜 |
| 有基线 | 优化前先记录当前指标，否则无法判断有没有用 |
| 有阈值 | 提升 < 20% 的改动回滚——不值得为此增加复杂度 |
| 不过早 | 数据量没到瓶颈前，先写清晰的代码 |
| 记下来 | 每处优化在代码里注明"为什么这么写" |

> **本项目的第一目标是能跑 + 有测试。**
> 性能优化属于 M7 之后的锦上添花，**不要因为优化牺牲代码可读性**。

| 指标 | 目标 | 测量方式 |

## 2. 已知瓶颈与优化手段

### 2.1 数据库查询 ⭐ 最常见

| 问题 | 症状 | 优化 |
|:---|:---|:---|
| N+1 查询 | 会话列表 50 个 → 51 次查询 | `selectinload()` 预加载，或单查询 JOIN |
| 深翻页 | `OFFSET 10000` 越来越慢 | **已用游标分页**（D4） |
| 缺索引 | `Seq Scan` | 见 `05-数据模型` 索引规划 |
| 查了不用的字段 | `SELECT *` | 只查需要的列 |
| 未读数实时 COUNT | 会话列表慢 | 冗余计数或缓存 |

**N+1 示例**

```python
# ❌ N+1：先查 50 个 room，再对每个查 last_message
rooms = await room_repo.list_by_user(user_id)
for r in rooms:
    r.last_message = await msg_repo.get(r.last_msg_id)   # 50 次查询！

# ✅ 单查询：一次性取出
stmt = (
    select(Room, Message)
    .join(RoomMember, RoomMember.room_id == Room.id)
    .outerjoin(Message, Message.id == Room.last_msg_id)
    .where(RoomMember.user_id == user_id)
    .order_by(Room.updated_at.desc())
)
```

**验证方式**

```python
# 测试中断言查询次数，防止 N+1 回归
async def test_room_list_no_n_plus_one(session):
    with assert_query_count(session, max_queries=3):
        await room_service.list_rooms(user_id)
```

### 2.2 慢查询排查

```sql
-- 开启慢查询日志（pg_stat_statements）
CREATE EXTENSION pg_stat_statements;

-- 查最慢的 10 条
SELECT calls, round(mean_exec_time::numeric, 2) AS avg_ms, query
FROM pg_stat_statements
ORDER BY mean_exec_time DESC
LIMIT 10;

-- 分析具体查询
EXPLAIN ANALYZE
SELECT * FROM messages WHERE room_id = 123 AND id < 10000 ORDER BY id DESC LIMIT 20;
```

**关注点**
- `Seq Scan` 出现在大表上 → 缺索引
- `rows` 估算与实际差 10 倍以上 → 统计信息过期，跑 `ANALYZE`
- `Buffers: shared hit/read` 高 → 考虑缓存或加索引

### 2.3 缓存策略

| 数据 | 缓存位置 | TTL | 失效时机 |
|:---|:---|:---|:---|
| 用户信息 | Redis | 5 分钟 | 用户改资料时删 |
| 敏感词库 | 进程内 | 5 分钟 | 词库更新时删 |
| 会话未读数 | Redis | 实时更新 | 读消息时更新 |
| 在线状态 | 进程内 | — | 连接断开时更新 |

> ⚠️ **本项目数据量小，缓存的主要价值是练手，不是必需。**
> 不要为了用缓存而用缓存——缓存一致性问题比性能问题更难查。

### 2.4 WebSocket 推送

| 问题 | 优化 |
|:---|:---|
| 大群广播慢（500 人） | 批量查询成员 → 并行推送（`asyncio.gather`） |
| 串行 await 每个连接 | 改用 `asyncio.gather(*[ws.send_json(d) for ws in conns])` |
| 序列化重复 | 同一条消息序列化一次，复用 bytes |

```python
# ❌ 串行
for ws in conns:
    await ws.send_json(data)      # 每个都要等序列化 + 网络

# ✅ 并行 + 序列化一次
payload = json.dumps(data)
await asyncio.gather(*[ws.send_text(payload) for ws in conns], return_exceptions=True)
```

### 2.5 敏感词算法对比（M7 的核心实验）

| 算法 | 构建复杂度 | 匹配复杂度 | 适用场景 |
|:---|:---|:---|:---|
| **DFA（Trie）** | O(总字符数) | O(文本长度) | 默认实现，简单够用 |
| **AC 自动机** | O(总字符数) | O(文本长度) | AC 有失败指针，理论上对多模式更优 |

**两者理论复杂度相同，实际差异在于常数因子与实现质量。**

压测脚本：

```python
@pytest.mark.benchmark
def test_compare_filters(benchmark):
    dfa = DFASensitiveFilter()
    ac = ACSensitiveFilter()
    words = load_words(10000)      # 1 万词
    dfa.load(words)
    ac.load(words)

    text = "正常文本内容" * 5000   # 约 3 万字

    r1 = benchmark.pedantic(dfa.filter, args=(text,), rounds=10, name="DFA")
    r2 = benchmark.pedantic(ac.filter, args=(text,), rounds=10, name="AC")
```

**记录结果到 `docs/perf/sensitive-benchmark.md`**，包含：
- 词库规模
- 文本长度
- 两者耗时与内存
- 结论（哪个更好、为什么）

> 这个实验的价值不在于选谁，而在于**学会用数据做技术决策**。

## 3. 压测方法

### 3.1 接口压测（Locust）

```python
# tests/perf/locustfile.py
from locust import HttpUser, task, between

class ChatUser(HttpUser):
    wait_time = between(1, 3)

    def on_start(self):
        resp = self.client.post("/api/v1/auth/login", json={
            "username": "loadtest", "password": "test1234"
        })
        self.token = resp.json()["data"]["access_token"]
        self.headers = {"Authorization": f"Bearer {self.token}"}

    @task(10)
    def list_messages(self):
        self.client.get(f"/api/v1/rooms/{self.room_id}/messages?limit=20",
                        headers=self.headers)

    @task(3)
    def send_message(self):
        self.client.post("/api/v1/messages", headers=self.headers,
                         json={"room_id": self.room_id, "type": 1, "content": "压测消息"})
```

### 3.2 WebSocket 并发压测

```python
# tests/perf/ws_load.py
import asyncio, websockets

async def one_client(token: str, duration: int = 30):
    async with websockets.connect(f"ws://localhost:8000/ws?token={token}") as ws:
        end = time.time() + duration
        while time.time() < end:
            await ws.recv()

async def main(n: int):
    tokens = [make_token(i) for i in range(n)]
    await asyncio.gather(*[one_client(t) for t in tokens])

asyncio.run(main(1000))     # 1000 连接
```

## 4. 性能检查清单

每个里程碑完成后跑一遍：

- [ ] 新增查询都走了索引（`EXPLAIN ANALYZE` 验证）
- [ ] 无明显 N+1（用查询计数断言）
- [ ] 接口 P99 在目标内

## 5. 什么时候不要优化

| 情况 | 建议 |
|:---|:---|
| 数据量 < 1 万行 | 索引建好就行，别搞分库分表 |
| 接口 QPS < 10 | 不需要缓存 |
| 优化会显著增加代码复杂度 | 提升 < 20% 就别做 |
| 没有 profiling 数据 | 先测，别猜 |

> **过早优化是万恶之源**，但**不建索引不是"不过早优化"，是疏忽**。
> 索引、游标分页这些属于**正确的设计**，不是优化。

## 6. 扩展路径（超出本项目范围，仅记录）

如果将来要真正支持大规模，路径是：

| 阶段 | 改动 |
|:---|:---|
| 单机多进程 | 连接注册表移到 Redis；用 Redis Pub/Sub 广播 |
| 水平扩展 | 引入 MQ（Kafka/RocketMQ）替代 outbox 轮询 |
| 消息存储 | 分库分表（按 room_id 哈希）；冷热分离 |
| 读扩散/写扩散 | 大群用读扩散，小群用写扩散 |
| 全局 seq | 引入号段分配的 seq 服务 |

**这些都不在 MinIM 范围内。** 记在这里是为了知道"边界在哪"，
而不是"这个项目没做完"。

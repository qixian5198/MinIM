# 02 · 系统架构

> 定位：系统的骨架——分成几层、每层干什么、关键设计为什么这么定
> 状态：v1.0

---

## 1. 分层架构

```
┌──────────────────────────────────────────────────────────┐
│  客户端     React 18 + TS + Vite                          │
│             HTTP (REST)        WebSocket                  │
├──────────────────────────────────────────────────────────┤
│  接入层     Nginx：反向代理 / WS 升级 / IP 级频控           │
├──────────────────────────────────────────────────────────┤
│  API 层     FastAPI                                       │
│             ├─ Router：auth / user / room / message        │
│             ├─ Depends：认证 / 频控 / 分页 / 会话           │
│             └─ Middleware：请求 ID / 日志 / 异常兜底        │
├──────────────────────────────────────────────────────────┤
│  服务层     Service —— 业务编排，事务边界在这一层           │
│             ├─ Strategy：消息类型 / 敏感词算法              │
│             ├─ Adapter：entity ↔ DTO 转换                  │
│             └─ Event：领域事件发布（进程内）                │
├──────────────────────────────────────────────────────────┤
│  数据层     Repository —— 唯一数据出入口                    │
│             SQLAlchemy 2.0 (async) + Alembic              │
├──────────────────────────────────────────────────────────┤
│  基础设施   PostgreSQL 16 │ Redis 7 │ MinIO │ Nginx        │
└──────────────────────────────────────────────────────────┘
```

### 依赖方向铁律

```
api  →  service  →  repository  →  db
```

**只能向下。** 违反示例（禁止）：
- service 里 import FastAPI 的 `Request` / `APIRouter`
- repository 里写业务判断（如"群主才能踢人"）
- api 层直接写 SQL

## 2. 模块划分

| 模块 | 职责 | 关键类 |
|:---|:---|:---|
| `auth` | 注册、登录、JWT 签发与校验 | `AuthService`, `TokenService` |
| `user` | 用户资料、好友、黑名单 | `UserService`, `FriendService` |
| `room` | 会话（单聊/群聊统一管理） | `RoomService` |
| `message` | 消息收发、历史、互动 | `MessageService`, `*MsgHandler` |
| `ws` | WebSocket 连接管理、推送 | `ConnectionManager` |
| `file` | 上传下载（MinIO） | `FileService` |
| `security` | 敏感词、频控、审计 | `SensitiveFilter`, `RateLimiter` |
| `outbox` | 本地消息表（可靠异步） | `OutboxService` |

## 3. 关键设计决策

### D1 · room 统一抽象单聊与群聊 ⭐ 最重要

```
room(id, type: single | group, name, avatar, owner_id, ...)
room_member(room_id, user_id, role, last_read_msg_id, ...)
message(id, room_id, from_uid, content, type, extra, ...)
```

**消息表只认 `room_id`，不区分会话类型。**

| 收益 | 说明 |
|:---|:---|
| 消除分支 | 发送/拉取/分页/推送全链路不需要 `if is_group` |
| 扩展容易 | 将来加"频道""客服会话"只是加一个 type |
| 权限统一 | 是否能读消息 = 是否是 `room_member` |

**代价**：单聊也需要两条 `room_member` 记录。这点冗余换来的简洁很划算。

### D2 · 消息类型用策略模式

```python
class MsgHandler(Protocol):
    msg_type: MessageType
    def validate(self, content) -> None: ...
    def build_extra(self, payload) -> dict: ...

# 工厂分发
handler = MsgHandlerFactory.get(msg_type)
```

新增消息类型 = 加一个 Handler 类，不改老代码。

### D3 · 消息与互动解耦

点赞/点踩不写在 `message` 表，独立 `message_mark`：
- 加"收藏""转发"等新互动，不动消息主表
- 消息表保持"不可变"语义，利于缓存

### D4 · 游标分页，禁止 offset

```sql
-- ✅ 正确
SELECT * FROM messages
WHERE room_id = :room_id AND id < :cursor
ORDER BY id DESC LIMIT 20;

-- ❌ 禁止
SELECT * FROM messages ... LIMIT 20 OFFSET 1000;
```

offset 在深翻页时会扫描并丢弃大量行，IM 场景下必然崩。

### D5 · 本地消息表（Outbox）解决一致性

```
业务事务内：
  ├─ 写业务表（如 messages）
  └─ 写 outbox 记录（同事务）

后台任务：
  ├─ 轮询 outbox 未发送记录
  ├─ 投递到 MQ / 执行异步动作
  └─ 成功则标记，失败则重试（带退避）
```

解决"数据库事务成功但异步动作失败"的经典问题。M6 实现。

### D6 · 敏感词：DFA 为主，预留 AC

| 算法 | 特点 | 用途 |
|:---|:---|:---|
| DFA（确定有穷自动机） | 实现简单、易调试 | **默认实现** |
| AC 自动机 | 多模式匹配理论最优 | M7 实现并做压测对比 |

两者实现同一接口，可切换、可对比。这是本项目最有价值的性能实验。

## 4. WebSocket 架构

```
                    ┌─────────────┐
   Client A ───────▶│             │◀─────── Client B
   Client C ───────▶│  Connection │◀─────── Client D
                    │   Manager   │
                    └──────┬──────┘
                           │
                    ┌──────▼──────┐
                    │  user_id →  │
                    │ [conn, ...] │   支持多设备/多标签页
                    └─────────────┘
```

| 关注点 | 方案 |
|:---|:---|
| 认证 | 握手时校验 JWT（`WS /ws?token=xxx`） |
| 连接存储 | 进程内 dict：`user_id → Set[WebSocket]` |
| 心跳 | 客户端 30s ping，服务端 60s 超时清理 |
| 水平扩展 | **当前不支持**（单机）；扩展需引入 Redis Pub/Sub，见 12 性能优化 |
| 断线补偿 | 重连带 `Last-Seq`，补发 `seq > Last-Seq` 的消息 |

> 单机限制是**有意为之**。多实例广播属于"分布式 IM"范畴，超出本项目范围。
> 在 `12-性能优化.md` 中记录了扩展路径，但不在 Must 范围。

## 5. 数据流：一条消息的完整旅程

```
1. Client A  POST /api/v1/messages   {room_id, type, content}
2. API 层    认证 → 频控 → 参数校验（Pydantic）
3. Service   校验 A 是 room 成员 → 敏感词过滤 → 写 messages（事务）
                                              → 写 outbox（同事务）
4. Service   更新 room 的 last_msg_id（便于会话列表展示）
5. 响应      返回消息对象给 A（A 自己不靠推送渲染）
6. 后台      Outbox 任务捞记录 → 查 room 成员 → 推送
7. WS        ConnectionManager 向每个在线成员的每个连接推送 message.new
8. Client B  收到推送 → 渲染
```

**为什么要 outbox 而不是直接推送？**
直接推送时，若推送抛异常会回滚掉已发送的消息——用户发了消息却消失。
解耦后：消息一定落库，推送失败可重试。

## 6. 技术约束与权衡

| 约束 | 原因 |
|:---|:---|
| 不引入 MQ（Kafka/RocketMQ） | 每多一个中间件，启动门槛高一分。用 Redis Stream + outbox 表足够 |
| 不引入 Elasticsearch | 无搜索需求 |
| 不引入 Celery | 后台任务用 FastAPI BackgroundTasks + APScheduler 足够 |
| 单机 WebSocket，不做多实例 | 分布式 IM 超纲；扩展路径已记录 |
| Docker Compose 而非 K8s | 练手项目，运维复杂度要低 |

## 7. 架构决策记录（ADR 摘要）

| # | 决策 | 备选方案 | 为什么选它 |
|:--:|:---|:---|:---|
| A1 | room 统一抽象 | 单聊群聊两张表 | 消除全链路分支 |
| A2 | 游标分页 | offset 分页 | 深翻页性能 |
| A3 | outbox 表 | 直接异步推送 | 保证消息不丢 |
| A4 | 进程内连接管理 | Redis 连接注册表 | 单机够用，复杂度低 |
| A5 | DFA 默认 | AC 自动机默认 | 先简单可跑，再优化 |
| A6 | 敏感词替换 | 拒绝发送 | 用户体验更好 |

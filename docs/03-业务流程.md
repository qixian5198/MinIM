## 2. 注册与登录

```mermaid
sequenceDiagram
    participant C as 客户端
    participant API as FastAPI
    participant S as AuthService
    participant DB as PostgreSQL
    participant R as Redis

    C->>API: POST /auth/register {username, password}
    API->>API: Pydantic 校验格式
    API->>R: 频控检查 (IP 10次/分)
    R-->>API: 通过
    API->>S: 注册
    S->>DB: 查询用户名是否存在
    DB-->>S: 不存在
    S->>S: bcrypt 哈希密码
    S->>DB: 插入 user
    DB-->>S: user_id
    S-->>API: 用户对象
    API-->>C: 201 {id, username}

    C->>API: POST /auth/login {username, password}
    API->>S: 校验
    S->>DB: 查询用户
    DB-->>S: user + password_hash
    S->>S: bcrypt 比对
    alt 密码正确
        S->>S: 签发 access_token + refresh_token
        S-->>C: 200 {access_token, refresh_token, user}
    else 密码错误
        S-->>C: 401 ERR_PASSWORD_WRONG
    end
```

**关键分支**
- 用户名已存在 → `409 ERR_USERNAME_TAKEN`
- 频控触发 → `429 ERR_RATE_LIMITED`
- 参数非法 → `422`（Pydantic 自动）

## 3. 发送消息（核心链路）

```mermaid
sequenceDiagram
    participant A as 客户端 A
    participant API as FastAPI
    participant S as MessageService
    participant F as SensitiveFilter
    participant DB as PostgreSQL
    participant OB as Outbox 任务
    participant WS as ConnectionManager
    participant B as 客户端 B

    A->>API: POST /messages {room_id, type, content}
    API->>API: 认证 + 频控(20/分)
    API->>S: send_message()
    S->>DB: 校验 A 是 room_member
    DB-->>S: 是成员
    S->>F: 敏感词过滤
    F-->>S: 过滤后内容
    S->>DB: 事务开始
    S->>DB: INSERT message
    S->>DB: INSERT outbox (待推送)
    S->>DB: UPDATE room.last_msg_id
    S->>DB: 事务提交
    S-->>A: 201 {message}

    OB->>DB: 轮询未发送 outbox
    DB-->>OB: 待推送记录
    OB->>DB: 查询 room 成员
    DB-->>OB: [A, B, C...]
    OB->>WS: 向在线成员推送
    WS->>B: WS message.new
    WS->>A: WS message.new (其他设备)
    OB->>DB: 标记 outbox 已发送
```

**为什么 A 也走推送？** 用户可能开多个标签页，其他标签页需要同步。
A 自己发消息的那个 tab 用 HTTP 响应渲染，不依赖推送（避免重复渲染）。

**失败处理**
- 事务失败 → 整体回滚，返回错误，消息不存在
- 推送失败 → 消息已落库，outbox 重试（指数退避，最多 5 次）
- 重试仍失败 → 标记 `dead_letter`，记录日志告警

## 4. WebSocket 连接生命周期

```mermaid
stateDiagram-v2
    [*] --> 连接中: WS /ws?token=xxx
    连接中 --> 已认证: token 校验通过
    连接中 --> 已关闭: token 非法 (4001)
    已认证 --> 在线: 加入 ConnectionManager
    在线 --> 在线: 心跳 ping/pong (30s)
    在线 --> 已关闭: 60s 无心跳 / 客户端断开
    已关闭 --> 连接中: 客户端重连 (带 Last-Seq)
    已认证 --> 在线: 补发 seq > Last-Seq 的消息
```

**重连补偿**
```
Client → Server: WS /ws?token=xxx&last_seq=12345
Server → Client: [补发 seq 12346, 12347, ...]
Server → Client: {"type":"sync.done"}
```

## 5. 好友申请

```mermaid
sequenceDiagram
    participant A as 用户 A
    participant API
    participant DB
    participant B as 用户 B

    A->>API: POST /friends/requests {to_uid, message}
    API->>DB: 校验：非好友 / 未拉黑 / 无待处理申请
    DB-->>API: 通过
    API->>DB: INSERT friend_request (pending)
    API->>B: WS friend.request.new

    B->>API: PUT /friends/requests/{id} {action: accept}
    API->>DB: 校验 B 是接收方
    API->>DB: 事务：更新 request=accepted
    API->>DB:       INSERT friendship (A→B)
    API->>DB:       INSERT friendship (B→A)
    API->>DB:       创建 room(single) + 2 条 room_member
    API->>DB: 事务提交
    API->>A: WS friend.request.accepted
```

**好友关系是双向两条记录**，查询好友列表时只查 `user_id = me`，避免 `OR` 查询（利于索引）。

**拒绝**：只更新 request 状态为 `rejected`，不建关系。

## 7. 加载历史消息（游标分页）

```mermaid
sequenceDiagram
    participant C as 客户端
    participant API
    participant S as MessageService
    participant DB

    C->>API: GET /rooms/{id}/messages?limit=20
    Note over API: 首次无 cursor
    API->>S: 查询
    S->>DB: WHERE room_id=? ORDER BY id DESC LIMIT 21
    Note over DB: 多查 1 条判断是否还有更多
    DB-->>S: 21 条
    S->>S: 取前 20 条，has_more = (len == 21)
    S-->>C: {list, next_cursor, has_more}

    C->>API: GET .../messages?cursor=880&limit=20
    API->>DB: WHERE room_id=? AND id < 880 ORDER BY id DESC LIMIT 21
    DB-->>S: 结果
    S-->>C: {list, next_cursor, has_more}
```

**`has_more` 判定技巧**：查 `limit + 1` 条，若返回满则说明还有下一页。
避免额外的 `COUNT(*)` 查询。

## 8. 已读回执

```mermaid
sequenceDiagram
    participant B as 客户端 B
    participant API
    participant DB
    participant A as 客户端 A

    B->>API: WS message.read {room_id, last_read_msg_id}
    Note over B: 进入会话 / 滚动到底时触发
    API->>DB: UPDATE room_member SET last_read_msg_id=?
    Note over DB: 只前进不后退 (GREATEST)
    API->>A: WS message.read {room_id, user_id, last_read_msg_id}
    A->>A: 消息状态由"已送达"变为"已读"
```

**只前进不后退**：
```sql
UPDATE room_member
SET last_read_msg_id = GREATEST(last_read_msg_id, :new_value)
WHERE room_id = :room_id AND user_id = :user_id;
```
防止客户端乱序上报导致已读回退。

## 9. 敏感词过滤（发送侧）

```mermaid
flowchart TD
    A[消息内容] --> B[DFA 扫描]
    B --> C{命中敏感词?}
    C -->|否| D[原样入库]
    C -->|是| E[替换为 ***]
    E --> F[记录审计日志]
    F --> D
    D --> G[正常发送流程]
```

> 策略为**替换**而非拒绝（决策 5）。用户不会遇到"消息莫名发不出去"的困惑。
> 审计日志保留原文 hash，便于追溯，不存明文。

## 10. 频控流程

```mermaid
flowchart TD
    A[请求进入] --> B{接口有频控注解?}
    B -->|否| C[放行]
    B -->|是| D[生成 key: 用户ID 或 IP + 接口]
    D --> E[Redis INCR + EXPIRE]
    E --> F{计数 > 阈值?}
    F -->|否| C
    F -->|是| G[429 + Retry-After 头]
```

| 接口 | 维度 | 阈值 |
|:---|:---|:---|
| `/auth/login` | IP | 10 次/分钟 |
| `/auth/register` | IP | 3 次/分钟 |
| `POST /messages` | 用户 | 20 条/分钟 |
| `POST /files` | 用户 | 10 次/分钟 |
| WS 连接 | IP | 20 次/分钟 |

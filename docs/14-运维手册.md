## 1. 监控指标

### 1.1 应用层

| 指标 | 采集方式 | 告警阈值 | 说明 |
|:---|:---|:---|:---|
| 健康检查 | `GET /health` | 连续 3 次失败 | 最基础 |
| 接口错误率 | 日志统计 5xx | > 1% | |
| 接口 P99 延迟 | 日志打点 | > 500ms | 持续 5 分钟 |
| WebSocket 连接数 | 进程内计数上报 | > 800（上限 1000） | |
| 消息发送速率 | 计数器 | 突增 10 倍 | 可能是被刷 |
| Outbox 积压 | `COUNT(status=0)` | > 1000 | 异步任务卡住 |
| Outbox 死信 | `COUNT(status=2)` | > 0 | 立即告警 |

### 1.2 基础设施

| 指标 | 命令 | 告警阈值 |
|:---|:---|:---|
| 容器状态 | `docker compose ps` | 非 `healthy` |
| CPU | `docker stats` | > 80% 持续 5 分钟 |
| 内存 | `docker stats` | > 80% |
| 磁盘 | `df -h` | > 85% |
| PostgreSQL 连接数 | SQL 查询 | > 80% max_connections |
| Redis 内存 | `redis-cli info memory` | > 80% maxmemory |

### 1.3 简易监控（无 Prometheus 时的方案）

```bash
# scripts/healthcheck.sh —— 加进 crontab，每 5 分钟跑
#!/usr/bin/env bash
BASE=http://localhost:8000

if ! curl -sf --max-time 5 "$BASE/health" > /dev/null; then
    echo "$(date): 健康检查失败" >> /var/log/minim-alert.log
    # 可以接邮件/钉钉/微信通知
fi
```

```cron
*/5 * * * * /path/to/scripts/healthcheck.sh
```

## 2. 日志规范

### 2.1 结构化日志

用 `structlog` 输出 JSON，便于检索：

```jsonc
{
  "timestamp": "2026-09-18T12:30:00.123Z",
  "level": "INFO",
  "event": "message.sent",
  "request_id": "req_7f3a9c",
  "user_id": 10001,
  "room_id": 50001,
  "msg_id": 881,
  "duration_ms": 23
}
```

### 2.2 必须记录的字段

| 字段 | 说明 |
|:---|:---|
| `timestamp` | ISO 8601，毫秒精度 |
| `level` | DEBUG / INFO / WARNING / ERROR |
| `event` | 事件名，用点分命名（`message.sent`） |
| `request_id` | **贯穿一次请求的所有日志**，排查利器 |
| `user_id` | 谁的操作 |
| `duration_ms` | 耗时 |

### 2.3 禁止记录的字段 ⚠️

| 字段 | 原因 |
|:---|:---|
| `password` / `password_hash` | 密码绝不能进日志 |
| `token` / `access_token` | token 泄露 = 账号被盗 |
| 身份证 / 手机号 | 隐私合规 |
| 完整请求体（含敏感字段） | 只记关键字段 |

**上线前必查**

```bash
grep -riE "password|token|secret" /var/log/minim/*.log | head -20
```

### 2.4 日志级别使用

| 级别 | 用途 | 示例 |
|:---|:---|:---|
| DEBUG | 开发调试，**生产关闭** | 变量值、SQL |
| INFO | 正常业务事件 | 消息发送、用户登录 |
| WARNING | 可恢复的异常 | 频控触发、重试成功 |
| ERROR | 需要关注但不致命 | 推送失败、文件上传失败 |
| CRITICAL | 系统不可用 | 数据库连接失败 |

### 2.5 日志轮转

```yaml
# docker-compose.prod.yml 中
logging:
  driver: "json-file"
  options:
    max-size: "50m"
    max-file: "5"
```

> 不配轮转，日志会把磁盘吃光。这是最经典的运维事故之一。

## 3. 备份策略

### 3.1 备份什么

| 对象 | 频率 | 保留 | 方式 |
|:---|:---|:---|:---|
| PostgreSQL | 每天 03:00 | 30 天 | `pg_dump` |
| Redis（AOF） | 每天 | 7 天 | `redis-cli BGREWRITEAOF` + 拷贝 |
| MinIO 文件 | 每周 | 4 周 | `mc mirror` |
| 配置文件 | 变更时 | 永久 | git（**密钥除外**） |

> ⚠️ **备份绝不能放在 exFAT 项目盘**（无 journal，掉盘即损坏）。
> 备份到**本地盘**或**异地**。

### 3.2 备份脚本

```bash
#!/usr/bin/env bash
# scripts/backup.sh
set -euo pipefail

BACKUP_DIR="$HOME/backups/minim"    # 本地盘，不是 SSD
DATE=$(date +%Y%m%d-%H%M%S)
mkdir -p "$BACKUP_DIR"

# 数据库
docker exec minim-postgres pg_dump -U minim minim | gzip > "$BACKUP_DIR/db-$DATE.sql.gz"

# 保留 30 天
find "$BACKUP_DIR" -name "db-*.sql.gz" -mtime +30 -delete

echo "备份完成: $BACKUP_DIR/db-$DATE.sql.gz"
```

```cron
0 3 * * * /path/to/scripts/backup.sh >> /var/log/minim-backup.log 2>&1
```

### 3.3 恢复演练 ⭐ 最重要

**没验证过的备份等于没备份。**

```bash
# 每季度做一次恢复演练
gunzip < backup/db-20260918.sql.gz | docker exec -i minim-postgres psql -U minim minim_test
# 验证数据完整性
docker exec minim-postgres psql -U minim -d minim_test -c "SELECT count(*) FROM users;"
```

**演练记录写进 `docs/ops/backup-drill.md`**，包含：演练时间、耗时、是否成功。

## 4. 常见故障与处理

### 4.1 服务不可用

```
现象：健康检查失败 / 接口 502

排查顺序：
1. docker compose ps               —— 容器是否在运行
2. docker compose logs app --tail 100   —— 应用日志
3. curl localhost:8000/health      —— 应用本身
4. docker compose logs postgres    —— 数据库是否异常
5. df -h                           —— 磁盘是否满
```

| 原因 | 处理 |
|:---|:---|
| 容器 OOM | `docker stats` 确认 → 加大内存限制或查内存泄漏 |
| 磁盘满 | 清理日志 / 旧备份 |
| 数据库连接池耗尽 | 查慢查询、长事务；调连接池大小 |
| 迁移失败 | 查日志 → `alembic downgrade` → 修复后重跑 |

---

### 4.2 WebSocket 连不上

```
现象：前端 WS 连接失败 / 立即断开

排查顺序：
1. 关闭码是什么？
   4001 → token 问题（过期/无效）
   4002 → 连接数超限
   4003 → 心跳超时
2. Nginx 配置是否有 Upgrade / Connection 头（见 13-部署上线）
3. 代理层是否限制了长连接超时
4. 服务端连接数是否已达上限
```

---

### 4.3 消息推送延迟

```
现象：消息发出去了，对方几秒后才收到

排查顺序：
1. Outbox 积压：SELECT count(*) FROM outbox WHERE status=0;
   积压多 → 后台任务卡住，查日志
2. 死信数量：SELECT count(*) FROM outbox WHERE status=2;
   有死信 → 查死信的 error 字段
3. Redis 连接是否正常
4. 大群广播慢 → 看是否 N+1 查询成员
```

---

### 4.4 数据库慢

```sql
-- 查当前活跃查询
SELECT pid, now() - query_start AS duration, state, query
FROM pg_stat_activity
WHERE state != 'idle' AND now() - query_start > interval '5 seconds'
ORDER BY duration DESC;

-- 杀掉慢查询
SELECT pg_cancel_backend(<pid>);        -- 温柔
SELECT pg_terminate_backend(<pid>);     -- 强杀

-- 查锁等待
SELECT * FROM pg_locks WHERE NOT granted;
```

---

### 4.5 Outbox 死信堆积

```sql
-- 查看死信
SELECT id, topic, retry_count, payload->>'error' AS error, created_at
FROM outbox WHERE status = 2 ORDER BY created_at DESC LIMIT 20;
```

| 处理 | 说明 |
|:---|:---|
| 修复后重投 | `UPDATE outbox SET status=0, retry_count=0 WHERE status=2 AND id=?` |
| 确认可丢弃 | 标记为已处理或直接删除（**要记录原因**） |

## 5. 日常运维任务

| 频率 | 任务 | 命令 |
|:---|:---|:---|
| 每天 | 检查健康检查 | `curl localhost:8000/health` |

| 每季 | 恢复演练 | 见 3.3 |

## 6. 应急联系人与升级

| 级别 | 定义 | 响应 |
|:---|:---|:---|
| P0 | 服务完全不可用 / 数据丢失 | 立即处理 |
| P1 | 核心功能受损（发不了消息） | 1 小时内 |
| P2 | 部分功能异常 | 当天 |
| P3 | 体验问题 | 排期 |

**本项目只有一个人（你），所以**：
- P0/P1：立刻修，先止损（回滚）再查原因
- P2/P3：记下来，有空再修

## 7. 运维文档维护

| 文档 | 更新时机 |
|:---|:---|
| 本文档 | 处理完一次故障后，**把排查过程补进去** |
| `docs/ops/incidents.md` | 每次 P0/P1 故障记录一条 |
| `docs/ops/backup-drill.md` | 每次恢复演练后 |

**故障记录模板**

```markdown
## 2026-09-18 消息推送延迟 30 秒

**现象**：用户反馈消息要等半分钟才收到
**影响**：全部会话，持续 2 小时
**根因**：Outbox 后台任务因一个未捕获异常退出，没有人拉起
**止损**：手动重启后台任务
**根治**：给后台任务加 try/except + 自动重启；加 Outbox 积压告警
**教训**：后台任务的异常必须有兜底，否则静默死亡
```

> **不记录故障 = 同一个坑会踩第二次。**

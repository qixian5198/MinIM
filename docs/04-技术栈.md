## 2. 刻意不引入的技术

| 不引入 | 原因 |
|:---|:---|
| Kafka / RocketMQ / RabbitMQ | 每多一个中间件，启动门槛高一分。**MallChat 就是死在这上面。** 用 Redis Stream + outbox 表足够 |
| Elasticsearch | 无搜索需求 |
| Celery | 后台任务用 FastAPI BackgroundTasks + APScheduler 足够；引入 Celery 要多维护 worker |
| K8s / 服务网格 | 单机 Compose 足够；运维复杂度要低 |
| GraphQL | REST + WebSocket 已够，无复杂聚合查询需求 |
| ORM 层的软删除插件 | 手写 `deleted_at` 更可控，避免魔法 |

**原则：能不加就不加。每加一个依赖，都要说出它解决了什么非它不可的问题。**

## 4. 版本管理策略

| 项 | 策略 |
|:---|:---|
| Python | 3.12（`pyenv` 或系统自带均可，写入 `.python-version`） |
| 依赖 | `pip-tools` 从 `requirements.in` 编译出锁定版 `requirements.txt` |

| 锁文件 | `requirements.txt` 必须提交进 git |

## 5. 为什么选 FastAPI 而不是 Flask / Django

| 框架 | 判断 |
|:---|:---|
| **FastAPI** | ✅ 原生 async + WebSocket + Pydantic 校验 + 自动 OpenAPI。本项目三个核心需求（WS、校验、文档）它都自带 |
| Flask | ❌ WebSocket 要靠 flask-sock，异步支持弱 |
| Django | ❌ 太重；Channels 做 WS 配置复杂，会淹没练习重点 |

## 6. 为什么选 PostgreSQL 而不是 MySQL

| 维度 | PostgreSQL | MySQL |
|:---|:---|:---|
| JSONB | ✅ 原生支持、可索引 | JSON 支持较弱 |
| 窗口函数 | ✅ 完整支持 | 8.0+ 才有 |
| 游标分页 | ✅ 都一样 | ✅ |
| Docker 镜像 | ✅ 官方 | ✅ |

**决定性因素**：消息的 `extra` 字段需要 JSONB 存扩展信息（不同类型消息结构不同）。
另外 `GREATEST()`、CTE 等在 PG 里用起来更顺手。

## 9. 环境相关的硬约束（exFAT 项目盘）

项目位于 `/Volumes/SSK SSD/MinIM`，该盘为 **exFAT**。这带来几条硬约束：

| 约束 | 影响 | 对策 |
|:---|:---|:---|
| 无 Unix 权限位 | git 会认为所有文件 777，产生 mode change 噪音 | `git config core.fileMode false` |
| 无 journal，掉盘易损坏 | 不能放活跃写数据库 | **数据库/Redis 数据全部走 Docker volume（在本地盘）** |
| 符号链接支持但性能一般 | node_modules 大量软链 | **前端依赖装在本地，或用 Docker 卷** |
| 文件名大小写不敏感 | `User.py` 与 `user.py` 冲突 | 文件名全小写 + 下划线 |
| 无硬链接 | pip/uv 的硬链接缓存失效 | 设置 `PIP_NO_CACHE_DIR` 或缓存指向本地盘 |

**结论**：SSD 上只放**源码 + 文档 + git**。
运行时产物（venv、node_modules、数据库数据）一律走本地盘或 Docker volume。
详见 `09-环境搭建.md`。
